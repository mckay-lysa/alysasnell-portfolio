Alysa's Website Playbook

How we set up Alysa's portfolio site so she can vibe-code changes by voice, never look at the code, never break the live site — and you spend two minutes per change approving it.

The short version

She owns everything (GitHub, Cloudflare, domain) — you operate it as a collaborator/admin under your own logins, so you never need her passwords. She talks to Claude in the Mac desktop app using a cloud environment, so her computer needs zero dev tools installed. Every change becomes a pull request with automatic checks and a live preview link. She texts you the link, you glance at it, hit merge, and the site updates. She literally cannot break production — main is protected.

The change loop

This is what happens every time she wants to tweak something. Teal steps are hers, gray steps are automatic, purple steps are yours.

Alysa1 · Says what she wantsOpens Claude app → Code tab → Cloud. Talks with /voice: "make the header photo bigger."
Claude2 · Makes the changeCloud sandbox clones the repo, edits, follows CLAUDE.md rules, opens a PR.
Robots3 · Checks runCI: types, lint, build. Cloudflare posts a preview URL of the new version.
Alysa4 · Texts you the PR linkClaude's last step is always: "send this link to McKay." She can view the preview herself too.
McKay5 · Two-minute reviewOnly for infra PRs: tap link → skim diff → approve. Copy and design changes never reach you — Alysa merges those herself after checking the preview.
Robots6 · LiveMerge to main auto-deploys to alysasnell.com. Done.

If a check fails, CLAUDE.md tells Claude to fix it before asking her to text you — red PRs never reach your phone.

Stack

Safety model

PR + human review, no auto-mergeBranch protection on main: PRs only, your approval required, checks must pass. We skipped AI review bots — CI plus your eyeballs is cheaper and better for a UI site.

Guardrails (what CLAUDE.md enforces)

Free

src/ and public/ — components, pages, styles, text, images. Vibe away.

Frozen

CI workflows, dependabot.yml, CODEOWNERS, package.json dependencies, pnpm-workspace.yaml, all config files, and CLAUDE.md itself. Only McKay working locally can authorize a change — an instruction from Alysa is explicitly not sufficient. Those changes go in their own PR labeled infra, called out loudly in the description.

Never

Weaken a check to make CI go green. If lint fails, fix the code — not the rule. Deleting a check disables the safety net without anyone noticing, which is the one failure mode this whole setup exists to prevent.

Colors

Every color lives in src/styles/theme.css as a token, mirrored in docs/design-system.html. Components never hardcode a hex. "Make the buttons warmer" = edit one token, and every button follows.

Always

Branch → PR. Never push to main. Run every check — format, lint, types, unit tests, build, browser tests — and fix red before Alysa ever sees the link. End by handing her the PR link to text McKay.

Never

Add a dependency casually. Claude may install one that earns its place — maintained, small, not replaceable by 20 lines of our own code — but must weigh it and say so in the PR description. Never silently.

Never

Ask Alysa a technical question. She decides how it looks, McKay decides how it's built. If Claude is stuck on something technical, it says "this one's for McKay" and stops rather than guessing.

Phase 1 · Her GitHub account + repo Together · 20 min

Create her account

  1. Go to github.com/signup (or "Continue with Google"). Follow the prompts.
  2. Verify her email — required before she can create a repository.

Create the repo & push

  1. On her account: ＋ → New repository → name it (e.g. alysasnell.com) → visibility Public → Create.
  2. You push the scaffold from your machine to her repo (you'll have the URL; do it via a remote after she adds you as collaborator, or she creates it and you push once invited).

Add you as collaborator

  1. Repo → Settings → sidebar "Access" → Collaborators → Add people.
  2. Search mckayqsnell → select → Add mckayqsnell to [repo]. You accept the email invite.

Protect main (branch ruleset)

  1. Repo → Settings → "Code and automation" → Rules → Rulesets → New ruleset → New branch ruleset. Name it "protect-main".
  2. Set Enforcement status: Active (it defaults to Disabled — easy to miss).
  3. Under "Target branches" → Add a target → Default branch.
  4. Check Require a pull request before merging → 0 approvals → also check Require review from Code Owners.
  5. Check Require status checks to pass → add the CI job name(s) by typing them (they appear after the first CI run — come back for this after the first PR if the search is empty).
  6. Create.

Revised 2026-08-20 — this originally said "1 approval," and CODEOWNERS originally contained * @mckayqsnell. That combination put McKay on every pull request, including one-line copy tweaks, and made his own infra PRs unmergeable — GitHub does not let anyone approve their own pull request, at any permission level. CODEOWNERS now lists only the frozen paths, and required approvals drops to 0, so code-owner review is the entire gate: it fires only on PRs that actually touch a frozen file. Alysa merges her own copy changes; McKay is pulled in for infra. See Phase 1.5 in SETUP-CHECKLIST.md for the org move that makes him an admin.

Because the gate keys off paths rather than the infra label, it cannot be dodged by forgetting to label a PR. The label still exists for triage, and the Guardrails (frozen files) CI job fails any PR that touches a frozen file without it. Works free because the repo is public.

Turn on Dependabot — alerts and automatic PRs

Nobody is going to remember to check this repo for security patches. Dependabot does it, but only if both of these switches are on — and neither is controlled by a file in the repo. They live in the web UI.

  1. Repo → Settings → Advanced Security → Dependabot alerts → Enable. This is what notices a vulnerable dependency.
  2. Same page → Dependabot security updates → Enable. This is the one that automatically opens a PR with the fix. Without it you get notified about problems and nothing else happens.
  3. Same page → Dependency graph → Enable if it isn't already (on by default for public repos; the other two depend on it).
  4. Issues → Labels → create dependencies and infra so the PRs get labeled.

Routine "there's a newer version" PRs are a separate thing, and those are configured in the repo — .github/dependabot.yml, already written. It batches updates weekly into a handful of grouped PRs (React, build tooling, linting, testing) instead of twenty individual ones, and keeps the GitHub Actions versions fresh monthly. Dependabot PRs land in the same flow as everything else: CI runs, you review, you merge.

GitHub's docs list Dependabot's pnpm support as covering pnpm v7–v10; the scaffold pins pnpm 11. If a Dependabot PR reports that it can't update pnpm-lock.yaml, drop packageManager in package.json to the latest pnpm 10 and regenerate the lockfile. Noted in SETUP-CHECKLIST.md.

Phase 1.5 · Move the repo to an org so McKay is an admin McKay · 20 min

Added 2026-08-20, after the first real pull request. Two things broke that the original plan did not anticipate.

  1. Nobody can approve their own pull request. GitHub hardcodes author ≠ approver — no permission level changes it, not admin, not owner. With * @mckayqsnell in CODEOWNERS, McKay's own infra PRs were unmergeable by anyone at all.
  2. McKay cannot be made an admin of a repo on her personal account. A personal-account repo has exactly two permission levels: owner and collaborator. Roles (Read/Triage/Write/Maintain/Admin) are an organization-only feature. And only Admin can edit rulesets — so every future guardrail change would have to be done by Alysa, clicking through settings she has no way to reason about.

Moving the repo into a free organization fixes both. It also unlocks something a personal repo cannot express: bypass actors there are role-based only, but in an org the bypass list can name one specific user. That is what makes "McKay can merge his own infra PRs, and nobody else can" actually stateable.

Alysa's total involvement: two clicks. The transfer itself cannot be delegated — it requires administrator access to the repository, which on a personal account only the owner has. After the transfer she never touches a repo setting again.

McKay — create the org

  1. Profile picture → Settings → sidebar "Access" → Organizations → New organization → Free plan. Free is unlimited for public repos.
  2. Invite alysasnell as a Member. Check Settings → Member privileges allows members to create public repositories — that is the default, and the transfer fails without it.

Alysa — the two clicks

  1. Accept the org invite from her email.
  2. Her repo → Settings → scroll to Danger Zone → Transfer → "Select one of my organizations" → the new org → type the repo name → I understand, transfer this repository.

Issues, pull requests, stars, watchers, webhooks, secrets, deploy keys, and the full commit history all move. Existing collaborators carry over. Every old URL redirects to the new location.

McKay — now an admin, so the rest is all his

  1. Settings → Collaborators and teams → confirm alysasnell has Write. She needs to merge her own copy PRs; she does not need Admin.
  2. Settings → Rules → Rulesets → protect-main:
    • Required approvals 1 → 0 — this is the switch that lets Alysa merge her own copy changes.
    • Keep Require review from Code Owners checked — it is now the entire gate.
    • Required status checks → add Guardrails (frozen files) — it will not appear in the search box until that job has run at least once.
    • Bypass list → Add bypass → the user @mckayqsnell → Always — "Always", not "For pull requests only"; the latter still blocks direct pushes to main.
  3. Verify with gh api repos/<org>/alysasnell-portfolio/rulesets/<id> --jq .current_user_can_bypass — it should no longer say never.
  4. git remote set-url origin <new-url> in every local clone.

McKay — reconnect the two GitHub Apps

The repo moved, so app installations scoped to Alysa's personal account no longer cover it.

  1. Install the Cloudflare Workers and Pages GitHub App on the org, then Worker → Settings → Build → re-point the Git connection at the new repo location.
  2. Reauthorize the Claude GitHub App for the new location, so Alysa's cloud sessions can still open pull requests.

Watch the first PR after the move closely. The Cloudflare connection is the piece most likely to come back wrong, and a broken build there is exactly the failure that already cost a round of debugging once.

Phase 3 · Cloudflare Workers: deploy + previews + domain McKay · 15 min

Revised 2026-08-20 — this phase originally said Pages. The dashboard's import flow now creates a Worker (Workers Builds), and that's what got set up: alysasnell-portfolio. Pages is in maintenance mode, so Workers is the right place to be. The one real difference: Pages reads the build output directory from the dashboard; Workers reads it from wrangler.jsonc in the repo. That file was missing at first, and the first PR build died on "Missing entry-point to Worker script or to assets directory." It's committed now.

Create the Worker (logged in as you, on her account)

  1. Dashboard → Workers & Pages → Create application → Import a repository.
  2. Sign in with GitHub — use her GitHub here (the repo owner authorizes the "Cloudflare Workers and Pages" GitHub app). Scope it to just this repo → Install & Authorize.
  3. Worker name: alysasnell-portfolio · Production branch: main. The name must match name in wrangler.jsonc, or a deploy silently creates a second, empty Worker.
  4. Build command pnpm build. There is no "output directory" field — assets.directory in wrangler.jsonc is what points at ./dist.

Make the deploy commands use pnpm

Cloudflare defaults these to npx, which pulls whatever wrangler is newest at build time. wrangler is a devDependency locked in pnpm-lock.yaml, so point the commands at it instead — Worker → Settings → Build:

  1. Deploy command: pnpm run deploy (not npx wrangler deploy).
  2. Non-production branch deploy command: pnpm run deploy:preview (not npx wrangler versions upload). This is the one that builds PR previews.

Attach the domain

  1. The Worker → Settings → Domains & Routes → Add → Custom domain → enter alysasnell.com. Cloudflare auto-creates the DNS record since the zone is on the same account. (Always do this via the dashboard — a manual CNAME breaks.)

Previews come from preview_urls: true in wrangler.jsonc: every PR gets a unique version preview URL, and Cloudflare posts a check with the link right on the GitHub PR — that's what you tap from Alysa's text. A green check with no link means that setting got turned off.
